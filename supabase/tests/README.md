# 데이터 권한 검증

`npm ci` 후 프로젝트 루트에서 실행합니다.

```sh
node --test server/supabase.test.mjs server/supabase-db.test.mjs
```

`supabase-db.test.mjs`는 PGlite의 실제 PostgreSQL 엔진에 배포용 SQL 마이그레이션을 그대로 적용합니다. Supabase의 `auth.users`, `auth.uid()`, `storage.buckets`, `storage.objects`는 테스트용 스키마로 준비하며, 쿼리는 실제 `anon`/`authenticated` 역할로 실행합니다.

검증 범위:

- 미로그인·미인증 이메일 계정 차단, 가족 간 목록·파일 격리, 다른 앱의 느슨한 Storage 정책이 있는 경우에도 접근 차단
- 회원끼리만 프로필 확인, 초대 코드는 소유자만 조회·갱신, 만료·실패 횟수 제한
- 업로드 예약과 파일 생성·완료 순서, 중복 업로드, 파일 크기·보관량 제한, 실제 크기를 속인 예약 및 삭제 미정리 객체의 한도 우회 차단
- 삭제 권한, 삭제 표식 이후 업로드·완료 차단, 파일 정리 재시도
- 실제 기록 시각 보존, 자동 전사와 수동 편집의 업데이트 시각 구분
- 주소 등록자만 상세 주소 접근, 시연 지도와 실제 주소의 상태 구분

이 검증은 실제 PostgreSQL 권한·함수 실행이며, 호스팅된 Supabase Auth/Storage HTTP 서비스의 전체 검증은 아닙니다. 배포 후 실제 두 계정의 이메일 확인, 업로드·재생·삭제 및 다른 가족 계정의 접근 거부를 별도로 확인해야 합니다.

삭제 표식은 다른 멤버의 파일 접근을 즉시 차단합니다. Supabase Storage의 파일 삭제 API에는 조회 권한도 필요하므로, 원 작성자는 물리적 파일 제거가 끝날 때까지 삭제 대기 파일에 접근 권한을 유지합니다. 앱의 재생 API는 삭제된 기록을 누구에게도 제공하지 않으며, Storage 삭제 성공 뒤에만 삭제 완료를 응답합니다. 저장소 장애로 파일 정리가 실패하면 삭제 대기로 남아 재시도됩니다.

동시 업로드와 삭제의 극단적인 경합에는 운영상 한계가 있습니다. [Supabase Storage 구현](https://github.com/supabase/storage/blob/master/src/storage/uploader.ts)은 사용자 RLS 검사 후 별도 관리자 권한으로 최종 파일 행을 기록하며, [권한 검사 트랜잭션은 롤백](https://github.com/supabase/storage/blob/master/src/storage/database/pg.ts)됩니다. 삭제 완료 응답 직후 이미 진행 중이던 업로드가 마무리되고 해당 앱 서버가 정리 전에 강제 종료되면, 삭제 표식에 해당하는 원본 객체가 남을 수 있습니다. 앱 재생과 다른 가족 멤버의 접근은 계속 차단되지만 물리적 삭제 완료까지 보장하지는 않습니다. 운영자는 `still_deletions.storage_path`에 대응하는 잔류 객체를 주기적으로 확인하고 **Storage API**로 제거해야 합니다. 관리되는 `storage.objects` 테이블에 추가 트리거를 설치하지는 않습니다.

보관 한도는 사용자당 1,000개·256 MiB, 공간당 2,000개·1 GiB입니다. 파일 하나는 최대 16 MiB이며, 업로드 완료 전에는 선언된 파일 크기와 무관하게 16 MiB를 임시 예약합니다. 완료 시 실제 크기를 확인하고 그 크기로 계산합니다. 따라서 새 업로드에는 최소 16 MiB의 여유 공간이 필요합니다. 삭제 표식만 남고 물리적으로 제거되지 않은 객체도 16 MiB로 계산하여, 정리 실패가 보관 한도 우회로 이어지지 않게 합니다.
